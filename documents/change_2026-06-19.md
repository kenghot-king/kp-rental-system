# Change — Deposit Documents & Forfeit/Return Fixes (2026-06-19)

## Overview

A batch of four related changes to the rental deposit flow: a new **ใบมัดจำ (Deposit
Certificate)** document, making the receipt date reflect the **paid date**, treating
**unhold/forfeit as deposit settlement** for order completion, and fixing a **crash on
Return** when the deposit was held rather than paid in cash.

**Working assumption (for now):** no partial payments — **1 invoice = 1 payment = 1 receipt**.
True per-payment receipts are deferred (see [Deferred](#deferred-future-change)).

---

## Items

### 1. ใบมัดจำ (Deposit Certificate) document

Base it on the existing Thai invoice/receipt layout, with deposit-specific changes.

| Aspect | Current | Desired |
|--------|---------|---------|
| Title | ใบเสร็จรับเงิน / ใบกำกับภาษี | **ใบมัดจำ** |
| Bottom signature / "Received by" block | shown | **removed** |
| "No." field | invoice number (`o.name`) | **Sale Order number** |
| File name | default | **`Deposit Certificate-{SO no.}.pdf`** |

- Reference layout: [`report/report_invoice_thai.xml`](../addons/ggg_rental/report/report_invoice_thai.xml)
  — title at L40-42, signature block at L246-275.

### 2. Receipt "Date" = paid date

The ใบเสร็จรับเงิน/ใบกำกับภาษี "Date" must show the **paid date** (the reconciled payment's
date), not the invoice date.

- Today the receipt binds Date to `o.invoice_date`
  ([`report_invoice_thai.xml:97`](../addons/ggg_rental/report/report_invoice_thai.xml#L97)).
- Change it to the **reconciled payment's date** (`matched_payment_ids` / `reconciled_payment_ids`
  on `account.move`). With no partial payments there is exactly one payment, so the date is
  unambiguous. Fallback to `invoice_date` if no payment is found.
- **Forfeit needs no extra work:** the forfeit wizard already sets the hold payment's date to
  the forfeiture date ([`deposit_hold_forfeit_wizard.py:25`](../addons/ggg_rental/wizard/deposit_hold_forfeit_wizard.py#L25)),
  and that payment is what reconciles the deposit invoice — so the forfeit receipt shows the
  forfeiture date automatically. **The posted invoice's `invoice_date` is never touched.**

### 3. Unhold / Forfeit ⇒ deposit settled (order completion)

When the deposit is **unheld** (released) or **forfeited**, the order's deposit axis counts as
settled, so the order can reach **Complete**.

- **Already implemented** by the uncommitted edit in
  [`sale_order.py:337`](../addons/ggg_rental/models/sale_order.py#L337) — the deposit axis treats
  `payment_state == 'paid'` (forfeit) and `hold_state in ('released', 'cancelled')` (unhold) as
  settled. **Verify and keep**, no rewrite.

### 4. Return crash — "There's nothing left to pay"

Returning an order with a **held** deposit raises *"There's nothing left to pay for the selected
journal items…"* and aborts the whole Return.

- **Cause:** on return, the code creates a deposit credit note and, if `deposit_auto_refund` is
  on, calls `account.payment.register(...).create({})` to auto-refund
  ([`sale_order_line.py:561-566`](../addons/ggg_rental/models/sale_order_line.py#L561-L566)).
  For a **hold** deposit the invoice was never actually paid in cash, so the credit note nets to
  zero residual → the payment register raises the error.
- **Fix rule:** on return, create + auto-refund a deposit credit note **only when the deposit was
  paid in cash** (a real residual exists). For a **hold** deposit (released or forfeited), issue
  **no credit note**.

Resulting behavior:

| Deposit type | On Return | Document |
|--------------|-----------|----------|
| Cash-paid | refund | credit note (RINV) + payment |
| Hold → unhold (released) | release only | none |
| Hold → forfeit | already captured | none |

This single rule fixes both the **crash** (item 4) and the **forfeit-then-return double-refund**.

---

## Settled decisions

- No partial payments assumed; 1 invoice = 1 payment = 1 receipt.
- Receipt Date = paid date; fallback to `invoice_date` if no payment.
- Forfeit dates the **payment** (not the posted invoice) to the forfeiture date.
- Hold deposits never produce a credit note on return.

## Deferred (future change)

True per-payment receipts: one invoice → many receipts, each rendered from `account.payment`
with that payment's amount, a VAT-per-payment split, and a receipt running number.
